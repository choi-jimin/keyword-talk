## 1. 기본 개념

### 클라이언트 vs 서비스
- **클라이언트(앱)**: 사용자 휴대폰에서 실행, 요청을 **보내는** 쪽
- **서비스(서버)**: 하나의 업무 기능을 맡아 **따로 실행되는 서버 프로그램** (송금 서비스, 잔액 서비스, 유저 서비스 …)
- MSA에서는 서비스끼리 메서드 호출이 아니라 **네트워크(HTTP) 요청**으로 통신 → 그래서 호출 횟수가 곧 비용

### 게이트웨이
- 모든 클라이언트 요청이 반드시 지나가는 **입구** (클라이언트 영역과 서버 영역의 경계)
- URL 경로를 보고 목적지 서비스로 라우팅 (`/transfer/**` → 송금 서비스)
- 인증, 유저 정보 첨부 같은 **공통 작업을 한 곳에서 처리**
- 요청 하나당 **목적지 서비스 하나만** 호출. 그 뒤의 서비스 간 호출은 서비스가 직접 함

```
[휴대폰]           [서버 영역]
  앱 ──요청──▶ gateway ─▶ 송금 서비스 ─▶ 잔액 서비스
                 │
                 └─▶ 유저 서비스 (물어보면 답만 함)
```

### 같은 유저인 걸 어떻게 아나? → 토큰
- 앱은 모든 요청에 로그인 토큰(`Authorization: Bearer ...`)을 붙여 보냄
- 서비스는 "같은 유저가 또 왔다"를 기억하지 않음. 매 요청마다 토큰으로 누구인지 확인

### 헤더 릴레이
- 서비스가 다른 서비스를 호출할 때 **받은 헤더를 그대로 넘겨주는 것**
- 그래서 게이트웨이에서 붙인 정보가 뒤쪽 서비스까지 전달됨
- 슬라이드 7(MSA) "tracing — client 활용과 헤더 릴레잉"과 연결
- 보통 공통 HTTP 클라이언트 라이브러리에서 자동 처리

### 로컬 캐시 vs 리모트 캐시

| | 로컬 캐시 (Caffeine 등) | 리모트 캐시 (Redis 등) |
|---|---|---|
| 위치 | 내 애플리케이션 메모리 | 별도 서버 메모리 (네트워크로 접근) |
| 속도 | 나노초 (메서드 호출) | 보통 1ms 미만 (네트워크 왕복 + 직렬화) |
| 공유 | 인스턴스마다 따로 | 모든 인스턴스가 같은 데이터 |
| 정합성 | 인스턴스끼리 어긋날 수 있음 | 한 곳이라 일관적 |
| 재시작 | 사라짐 | 유지됨 |

- Redis가 리모트 캐시인 이유: **독립된 서버 프로그램**이라 TCP로 요청을 보내야 함 (같은 머신에 띄워도 별도 프로세스)
- **2단 캐시**: L1 = 로컬, L2 = Redis

### 히트 / 미스 / 히트율
- **히트(hit)**: 캐시에서 찾음 → 빠름
- **미스(miss)**: 캐시에 없음 → 원본까지 가서 가져오고 캐시에 저장
- **히트율** = 히트 수 / 전체 요청 수
- 캐시의 효과는 히트율로 결정됨. 캐시 운영 시 가장 먼저 보는 지표

### 노드 vs 샤드
- **노드**: 분산 시스템을 이루는 **서버 한 대** (어디에)
- **샤드**: 데이터를 나눈 **조각** (무엇을)
- 한 노드에 여러 샤드가 있을 수 있고, 한 샤드가 복제되어 여러 노드에 있을 수도 있음
- 실무에선 샤드 1개 = 노드 1개(+복제본)인 경우가 많아 섞어 쓰기도 함

## 2. 구조는 어떻게 진화했나?

> 전체 목표: **유저 서버 부하를 계속 줄이고, 유저 서버가 죽어도 서비스는 살아있게 하기**

### 단계별 요약

| 단계 | 구조 | 해결한 것 | 남은 문제 |
|---|---|---|---|
| ① | user server + remote cache | 유저 서버 → DB 구간 부하 감소 | 모든 서비스가 각자 유저 서버 호출 |
| ② | gateway + user server | "누구인지(인증)"를 입구로 모음 | 상세 정보는 서비스들이 여전히 각자 조회 |
| ③ | gateway + passport | "유저 정보 조회"까지 입구로 모음 | 게이트웨이가 요청마다 유저 서버 호출 |
| ④ | gateway + local cache + sticky session | 게이트웨이 → 유저 서버 호출까지 감소 | 유저 서버가 죽으면 캐시 미스 시 실패 |
| ⑤ | gateway + Redis + Cassandra | 유저 서버가 죽어도 버팀 (가용성) | fallback 시 오래된 정보로 동작 |

### ① user server + remote cache

```
서비스 → user server → Redis (hit) / DB (miss)
```

- Redis 역할: **유저 서버와 DB 사이에서 DB 대신 빠르게 답해주는 캐시**
- Redis는 유저 서버와 **별개의 서버**. 유저 서버(애플리케이션)가 Redis(저장소)를 옆에 끼고 사용
- 유저 정보는 **자주 읽히지만 잘 안 바뀌는** 데이터라 캐시에 적합
- 로컬 캐시가 아닌 Redis를 쓴 이유: 유저 서버 인스턴스 여러 대가 같은 캐시를 공유
- ✅ DB 부하는 해결 / ❌ 서비스들 → 유저 서버로 몰리는 요청은 그대로

### ② gateway + user server

```
앱 → gateway ─(토큰 확인 1회)→ user server
       ↓ X-User-Id: 123
     서비스들 (상세 정보 필요하면 각자 user server 조회)
```

- MSA라 서비스가 많고, 각 서비스가 유저 정보를 조회하고 있었음 → **게이트웨이에서 하나의 통신으로 묶음**
- 서비스가 유저 서버를 부를 때는 **토큰 인증 없이 유저 ID로 바로 조회** (`GET /users/123`)
  - 인증은 게이트웨이에서 이미 끝났기 때문
  - 단, 서비스 간 호출 통제(내부망, mTLS, whitelist)는 여전히 필요 → 슬라이드 10
- ①→② 효과
  - "누구인지만 알면 되는" 서비스들의 호출이 사라짐
  - 인증 로직이 한 곳에 모임 (보안 일원화, 잘못된 요청은 입구에서 차단)

### ③ gateway + passport

```
앱 → gateway ─(인증 + 유저 정보 1회)→ user server
       ↓ X-Passport: {userId, name, grade, ...}
     송금 서비스 ─(헤더 릴레이)→ 잔액 서비스   ← 유저 서버 호출 없음
```

- 게이트웨이가 가져온 정보를 다른 서비스가 다시 가져올 이유가 없음 → **passport 형식으로 뒤의 모든 서버에 전달**
- passport = 게이트웨이가 만들어 요청에 붙이는 **유저 정보 묶음** (비유: 이름·부서·직급이 적힌 출입증)
- 서비스는 헤더에서 꺼내 쓰기만 함
- 예외: passport에 없는 정보가 필요하거나, 반드시 최신이어야 할 때만 직접 조회

#### ② vs ③ 호출 수 비교 (예: 서비스 5개, 그중 2개만 상세 정보 필요)

| | 계산 | 합계 |
|---|---|---|
| ① | 5개 서비스 모두 토큰 확인 호출 | 5번 |
| ② | 게이트웨이 1번 + 상세 정보 필요한 2개 | 3번 |
| ③ | 게이트웨이 1번 | **1번** (서비스가 늘어도 고정) |

- 💡 숫자보다 중요한 차이: **의존성**
  - ②: 모든 서비스가 유저 서버에 직접 의존 → 유저 서버가 느려지면 연쇄 장애
  - ③: 유저 서버에 의존하는 곳이 **게이트웨이 하나뿐**
  - 그래서 ④(캐시), ⑤(fallback)를 게이트웨이에만 붙여도 전체 효과가 남

#### passport에 들어가는 것 (예시)

```
userId, name, age, grade, deviceId, authLevel, issuedAt, signature
```

- 대다수 서비스가 공통으로 쓰는 정보만 넣음 (많이 넣으면 모든 호출의 헤더 크기 증가)
- **요청 시점의 스냅샷**임
- 모든 서비스가 같은 방식으로 읽고 릴레이해야 해서 보통 **공통 라이브러리**로 제공

#### passport vs 앱 토큰(JWT 등)

| | 앱 토큰 | passport |
|---|---|---|
| 만드는 곳 | 로그인 서버 | 게이트웨이 |
| 범위 | 앱 ↔ 서버 (외부) | 서비스 ↔ 서비스 (내부 전용) |
| 수명 | 몇 시간~며칠 | 요청 하나 동안 |
| 내용 | 최소한 | 내부용이라 풍부함 |

#### passport 보안 문제
> 핵심: 서비스들이 passport를 **검증 없이 믿기** 때문에, 가짜를 넣을 수 있으면 다른 사람으로 행세 가능

| 위험 | 예시 | 대응 |
|---|---|---|
| 외부에서 가짜 헤더 주입 | 공격자가 `X-Passport: {userId: 999}`를 직접 넣어 보냄 | 게이트웨이가 외부에서 들어온 헤더를 **무조건 지우고 새로 생성** |
| 게이트웨이 우회 | 송금 서비스에 직접 요청 | 서비스는 **내부망**에만, **mTLS** |
| 내부 위조·변조 | 해킹된 내부 서비스가 조작 | 게이트웨이가 **서명**(HMAC 등), 서비스가 검증 |
| 개인정보 노출 | 헤더 통째로 로그에 남김, 외부 API에 릴레이 | 로그 **마스킹**, 외부 호출 시 제외 |

→ 1, 2번이 가장 기본

### ④ gateway + local cache + sticky session

```
요청 → gateway
        ├ 로컬 캐시 hit  → passport 생성 → 서비스로
        └ 로컬 캐시 miss → user server ─ Redis hit / DB
```

- 게이트웨이 → 유저 서버 호출 횟수 자체를 줄이려고 **게이트웨이에 로컬 캐시** 도입
- 히트율을 높이려고 **sticky session** 적용
- 이 단계의 Redis는 **유저 서버 뒤에 있는 것**. 게이트웨이가 직접 쓰지는 않음 (슬라이드 기준 해석)

#### 로컬 캐시가 생기면 passport는 필요 없나? → 아님
- **로컬 캐시**: 정보를 **어디서 가져오느냐** (유저 서버 대신 자기 메모리)
- **passport**: 정보를 **어떻게 전달하느냐**
- 로컬 캐시는 게이트웨이 프로세스 안에 있어서 다른 서비스가 접근 불가 → 여전히 passport로 전달해야 함
- ③은 서비스들 → 유저 서버 구간을, ④는 게이트웨이 → 유저 서버 구간을 줄임

#### 스티키 세션
- **같은 사용자의 요청을 항상 같은 서버 인스턴스로 보내는 방식**
- 왜 필요? 로컬 캐시는 인스턴스마다 따로라서, 요청이 여러 게이트웨이로 흩어지면 계속 미스 + 같은 데이터가 N군데 중복 저장
- 구현: 게이트웨이 앞의 **로드밸런서**가 결정
  - 쿠키 방식 / 해시 방식(유저 ID, 토큰) / IP 방식(모바일은 IP가 자주 바뀌어 부적합)
- 단점
  - 특정 인스턴스로 **부하 쏠림**
  - 배포·장애로 인스턴스가 내려가면 담당 유저들이 **한꺼번에 캐시 미스**
  - 스케일링 시 담당이 섞임 → **consistent hashing**으로 완화

#### Consistent Hashing
- 단순 해시(`유저ID % 서버수`)의 문제: 서버가 3→4대가 되면 **약 75%** 유저의 담당이 바뀜 → 캐시 미스 폭주
- consistent hashing
  1. 0~큰 수를 **원형 고리**로 생각
  2. 서버도, 유저도 해시해서 고리 위에 배치
  3. 유저는 **시계 방향으로 처음 만나는 서버**가 담당
- 서버 추가 시 **새 서버가 맡을 몫(약 25%)만** 이동, 서버 제거 시 그 서버 몫만 이동
- **가상 노드**: 서버 1대를 고리 위 수백 개 점으로 흩어 찍어서 부하 균등화
- Redis Cluster는 **해시 슬롯**(16384개)으로 같은 효과 → 슬라이드 "해시 태그로 SLOT 분배"와 연결

#### 로컬 캐시 관리
> 핵심: 로컬 캐시를 **"사라져도 되는 것"**으로 설계. 비어도 느려질 뿐 장애로 이어지지 않게

| 문제 | 대응 |
|---|---|
| 너무 많이 쌓임 (GC 부담, OOM) | **maximumSize** + eviction(LRU/LFU, Caffeine은 W-TinyLFU), **TTL**, 자주 쓰고 작은 데이터만 넣기 |
| 재시작하면 사라짐 | 뒤에 **Redis(L2)**, **롤링 배포**, **워밍업**(readiness probe) |
| 사라진 직후 요청 몰림 | **request coalescing**(첫 요청만 조회, 나머지는 대기), consistent hashing |

#### Caffeine
- **Java/Kotlin용 로컬 캐시 라이브러리** (Guava Cache 후속, Spring Boot 기본 지원)
- HashMap 대비: 크기 제한, TTL, 스레드 안전, 통계 제공

```java
LoadingCache<Long, UserInfo> userCache = Caffeine.newBuilder()
    .maximumSize(100_000)                      // 최대 크기 + eviction
    .expireAfterWrite(Duration.ofMinutes(5))   // TTL
    .recordStats()                             // 히트율 통계
    .build(userId -> userServer.getUser(userId)); // 미스 시 로딩 (request coalescing 자동)
```

- 다른 언어: Go ristretto, Python cachetools, Node.js lru-cache

### ⑤ gateway + Redis + Cassandra

```
요청 → gateway
        ├ 로컬 캐시 hit → passport
        └ miss
            ├ user server 정상 → 조회 + Cassandra에도 저장
            └ user server 장애 → Cassandra의 마지막 정보로 passport 생성
```

- 발표 내용: 유저 서비스나 **약관 서비스** 같은 필수 서비스가 **다운되더라도 나머지 서비스가 운영**될 수 있게 게이트웨이에 Redis + Cassandra 도입 → 시스템 전체의 **가용성(reliability) 향상**
- ④까지가 "유저 서버 **부하 줄이기**"였다면, ⑤는 "유저 서버가 **죽어도 버티기**"
- ④와의 차이: 게이트웨이가 **자체 저장소를 직접** 가짐

| 단계 | 게이트웨이가 직접 쓰는 저장소 | 유저 서버가 죽으면 |
|---|---|---|
| ④ | 로컬 캐시만 | 캐시 미스 순간 실패 |
| ⑤ | 로컬 캐시 + Redis + Cassandra | 자체 저장소로 버팀 |

#### Cassandra란?
- **여러 서버(노드)에 데이터를 나눠 저장하는 분산 NoSQL DB** (Facebook 개발, Apache 오픈소스)

| | MySQL | Cassandra |
|---|---|---|
| 구조 | primary가 쓰기 담당 | **모든 노드 동등 (마스터 없음)** |
| 노드 장애 | primary 장애 시 전환 필요 | 다른 노드가 바로 대신 |
| 확장 | scale-up 위주 | 노드 추가 (scale-out) |
| 쓰기 | 보통 | 매우 빠름 |
| 조회 | 자유로운 SQL, JOIN | 키 조회 최적화, JOIN 없음 |
| 일관성 | 강함 | 조절 가능 |

- 복제(보통 3개 노드), 디스크 기반이라 재시작해도 유지, 대용량도 메모리보다 저렴

#### 왜 Cassandra? (해석)
- fallback 저장소는 **원본이 죽어도 살아 있어야** 의미 있음 → 잘 안 죽는 저장소
- 게이트웨이는 모든 요청의 입구라 쓰기가 많음 → 쓰기에 강함
- "유저 ID로 꺼내기" = Cassandra가 가장 잘하는 조회
- 수천만 유저 정보를 메모리에 두면 비쌈 → 디스크 기반이라 감당 가능

#### ⑤의 계층 역할 (해석, 발표에서 구체적 언급 없음)
- 로컬 캐시: 가장 빠름, 인스턴스별, 휘발
- Redis: 빠름, 게이트웨이 인스턴스 공유, 비쌈
- Cassandra: 느리지만 튼튼하고 영구적, 최후의 보루

#### 고민할 점
- 장애 중엔 **오래된 정보**로 동작 → 어떤 정보는 fallback 허용, 어떤 건 실패시킬지 결정 필요 (약관 철회처럼 법적으로 민감한 건 신중)
- 일관성 수준 선택 (복제본 1개 응답 = 빠름 ↔ 과반수 응답 = 정확)
- 데이터 모델링: 조회 패턴을 먼저 정하고 테이블 설계

## 3. Remote–Local 정합성은?

### 발표 흐름
- 부하가 높으면 보통 "Redis 쓰면 되지"로 끝남
- 그런데 **Redis조차 버거워지는 규모**에서는 로컬 캐시를 앞에 추가
- 그러면 **stale을 어디까지 허용할지** 결정해야 함
- stale을 최소화하려고 **invalidation을 pub/sub이나 stream으로 전파**
- Redis도 로컬 캐시도 **메모리라 비쌈** → 히트율과 비용 효율의 균형 고민

### Stale이란?
- 원본은 바뀌었는데 **캐시에는 옛날 값이 남아 있는 상태**
- 예: 유저 서버에서 홍길동 등급이 VIP → 일반으로 바뀌었는데, 게이트웨이 A/B/C 로컬 캐시엔 여전히 VIP

### 해결 방법

**① TTL (유효기간)**
- "5분 뒤 지우기" → 뭘 놓쳐도 **최대 5분**만 틀림
- 단순하고 확실한 **안전망**. 단, 그 시간 동안은 틀린 정보

**② Invalidation (무효화 알림)**
- 원본이 바뀌는 순간 모든 인스턴스에 "지우세요" 전파

| | pub/sub | Stream |
|---|---|---|
| 비유 | 사내 방송 | 공지 게시판 |
| 특징 | 빠르고 간단 | 기록이 남아 읽은 위치부터 이어 읽기 가능 |
| 단점 | **녹음 안 됨** — 재시작·끊김 중엔 영영 놓침 (at-most-once) | 길이(MAXLEN), 읽은 위치 관리 필요 |

**실제로는 같이 사용**: 알림으로 대부분 즉시 갱신 + TTL로 놓쳐도 최대 N분 안엔 갱신

### 함정
- **순서 문제**: DB 커밋 전에 무효화하면 다른 요청이 옛 값을 다시 채울 수 있음 → 커밋 후 발행, 버전·타임스탬프 비교
- **값 전달 vs 삭제 전달**: "지워라"만 보내고 다음 조회에서 다시 채우는 게 순서 문제에 더 안전
- **Thundering herd**: 무효화 직후 모든 인스턴스가 동시에 원본으로 몰림

### "stale 범위 관리" = 얼마나 틀려도 괜찮은가를 정하는 것

| 데이터 | 허용 | 방법 |
|---|---|---|
| 프로필 사진 | 몇 분 늦어도 OK | TTL만 |
| 등급, 권한 | 빨리 반영돼야 함 | TTL + 알림 |
| 잔액 | 틀리면 안 됨 | 로컬 캐시 X |

### 누가 정하나?
- 구현은 개발자, 하지만 **"틀렸을 때 무슨 일이 생기나"는 비즈니스 영역** → 개발자가 주도해서 기획·사업·법무와 함께 결정
- 개발자의 역할: 데이터 분류, 비용 계산(TTL 5분 → 10초면 호출 30배 증가 등), 선택지 제시, 구현과 모니터링
- 대부분은 개발자가 상식선에서 정해도 되고, **돈·권한·법**과 얽힌 것만 함께 논의

### 잔액은?
- 잔액은 유저 서버가 아니라 **잔액(계좌) 서비스의 DB**가 원본
- 송금 전 잔액 확인처럼 **판단에 쓰는 값**은 무조건 원본 + **락/트랜잭션** (동시 송금 두 건이 모두 "잔액 충분"으로 판단하는 걸 방지) → 슬라이드 6 "정합성은 어떻게 지킬까?"
- 화면에 보여주기만 하는 잔액은 서비스에 따라 아주 짧게 캐시하기도 함. 단, 그 값으로 돈이 움직이는 판단은 절대 X
- 같은 데이터라도 **어디에 쓰이느냐**에 따라 허용 범위가 다름

## 4. 메모리가 크다면?

### 발표 흐름
- Redis에 그냥 쌓아도 되지만 **메모리를 어떻게 줄일지** 고민
- "이 데이터에 맞는 자료구조가 뭐지?"를 **계속 질문**하면서 bitmap 같은 구조 선택, hotkey 관리
- **바이너리 포맷**을 쓰면 일반 문자열(JSON)보다 많이 줄어듦 → **팀 가이드로 지정**해서 메모리 절약

### Bitmap — 출석부처럼 체크만
- 일반 방식: 유저마다 키 하나 (`접속:2026-11-11:유저123 = 예`) → 키당 수십 바이트, 1억 명이면 수 GB
- Bitmap: 키 하나에 **유저 ID 위치의 칸(1비트)만 체크** → 1억 명이어도 **약 12.5MB**

```
SETBIT   접속:2026-11-11 123 1   # 123번 유저 접속 체크
GETBIT   접속:2026-11-11 123     # 접속 여부 확인
BITCOUNT 접속:2026-11-11         # 오늘 접속자 수
```

- **예/아니오** 데이터에만 사용 가능 (출석, 알림 동의 여부 등)

#### 칸 위치는 어떻게 정하나? → 보통 유저 숫자 ID
- Bitmap은 **가장 큰 칸 번호까지 공간을 잡음** → ID가 0 근처부터 빽빽해야 효율적

| ID 형태 | 적합도 | 방법 |
|---|---|---|
| 1부터 빽빽한 숫자 | 아주 좋음 | ID 그대로 |
| 큰 숫자에서 시작 | 괜찮음 | 시작점을 빼서 사용 |
| UUID, 문자열 | 바로 불가 | ID → 일련번호 매핑 표 |
| 매우 띄엄띄엄 | 비효율 | 구간별 키 분할, Set, Roaring Bitmap |

- Redis Bitmap 칸 번호 최대 약 42억(2³²)

### Hotkey — 한 계산대에만 줄이 길어지는 문제
- Redis Cluster에서 키 하나는 **한 샤드에만** 있음 → 인기 키(이벤트, 공지, 환율 등)에 요청이 몰리면 그 노드만 과부하
- 대응
  - **로컬 캐시**에 두어 Redis까지 안 가게
  - **키 복제** (`이벤트:1`, `이벤트:2`, …로 나눠 읽기)
  - replica에서 읽기
- **Big key**: 키 하나에 데이터가 너무 많음 → 쪼개서 여러 키에
- 탐지: `redis-cli --hotkeys`, `--bigkeys`, `MEMORY USAGE`

### Binary 포맷 — 매번 질문까지 적지 않기
- JSON은 항목 이름이 유저마다 반복되고 숫자도 글자로 저장 → 큼
- **직렬화**: 객체를 저장 가능한 바이트로 바꾸는 것 (역직렬화는 반대)
- Protobuf, MessagePack은 Redis 같은 **서버가 아니라 포맷/라이브러리** (Redis = 창고, 포맷 = 포장 방식)

```
UserInfo 객체 ─(직렬화)→ 바이트 ─(저장)→ Redis
Redis ─(꺼냄)→ 바이트 ─(역직렬화)→ UserInfo 객체
```

#### JSON vs MessagePack vs Protobuf

| | 저장하는 것 | 해석 |
|---|---|---|
| JSON | 항목 이름 + 값 (글자 그대로) | 그냥 읽힘 |
| MessagePack | 항목 이름 + 값 (압축된 바이트) | 라이브러리로 풀면 됨 ("압축한 JSON") |
| Protobuf | **필드 번호 + 값** (압축된 바이트) | **양식(.proto) 파일이 있어야** 해석 |

```proto
message UserInfo {
  int64  userId = 1;
  string name   = 2;
}
```

```
JSON:        {"userId":123,"name":"홍길동"}
Protobuf:    [1번][123] [2번][홍길동]   ← 이름 대신 1바이트 번호
```

- 번호를 붙이는 이유: 양식 변경 대응
  - 새 필드(3번) 추가해도 옛 서버는 모르는 번호를 건너뜀
  - 빈 값은 생략 가능
  - 규칙: **한 번 쓴 번호는 다른 의미로 재사용하지 않기**
- 단점: 사람이 읽을 수 없음, 스키마 호환성 관리 필요
- Protobuf는 gRPC 기본 포맷이기도 함. Avro도 같은 계열

| | Protobuf | MessagePack |
|---|---|---|
| 스키마 | 필수 | 불필요 |
| 크기 | 더 작음 | 작음 |
| 사용 편의 | 양식 파일 관리 필요 | JSON처럼 바로 사용 |

#### 토스는?
- 발표에서 확인된 것: **Redis 저장 시 바이너리 포맷 사용을 팀 가이드로 지정**
- 구체적인 포맷은 언급 없음. 다만 슬라이드 9(CPU/Memory)에 avro, protobuf 등장
- 인터뷰에선 단정하기보다 **포맷 선택 기준**을 본인 관점으로 설명하기 (스키마 관리 감수 여부, 크기, 다른 언어 호환, 스키마 변경 빈도)

### 정리

| 방법 | 비유 | 효과 |
|---|---|---|
| Bitmap | 메모지 대신 출석부 체크 | 예/아니오 데이터를 수백 배 축소 |
| Hotkey 관리 | 인기 상품 계산대 늘리기 | 한 노드에 몰리는 부하 분산 |
| Binary 포맷 | 매번 질문 안 쓰고 양식지 | 데이터 크기 절반 이하 |

→ 같은 메모리에 더 많이 담을수록 **비용 감소 + 히트율 상승**

## 5. 한 줄 요약

> **유저 서버 부하 감소** (묶기 → passport → 로컬 캐시 + sticky)
> → **장애 격리** (Cassandra fallback)
> → 로컬 캐시 도입으로 생긴 **정합성 문제** (stale 범위 + invalidation 전파)
> → 이 모두를 떠받치는 **메모리 비용** (자료구조 선택, 바이너리 포맷)

## 6. 다른 슬라이드와 연결

| 개념 | 연결 슬라이드 |
|---|---|
| 해시 슬롯, consistent hashing | Cache — 해시 태그로 SLOT 분배 |
| 히트율 | Cache — 운영·장애 대응 (hit rate) |
| 헤더 릴레이 | MSA — tracing, 헤더 릴레잉 |
| passport 보안, 서비스 간 통제 | 보안/인증 — mTLS, whitelist |
| 로그 마스킹 | 로그/메트릭 — masking |
| 잔액 정합성, 락 | DB/Storage — 정합성은 어떻게 지킬까? |
| 바이너리 포맷, 스키마 | CPU/Memory — avro, protobuf, schema 운영 |
| 롤링 배포, graceful shutdown | Kafka — 안정적으로 배포하려면? |
