## 0. 슬라이드 원문

| 질문 | 키워드 |
|---|---|
| 가져올 데이터가 많다면? | 해시 태그로 SLOT 분배, MGET 요청 최적화 |
| 원자적 처리가 필요하다면? | lua script 활용 |

### 강의 내용 (전사문 요약)
- Redis에서 가져올 데이터가 많을 때 **어떻게 분배**하고, 가져올 때 **라운드 로빈을 최소화**할 수 있을지 고민
- **MGET 같은 것들이 라이브러리에서 실제로 어떻게 구현되어 있는지** 직접 까보고, **해시 태그로 SLOT을 분배**해서 Redis 분산도 적절하게 유지
- **단일 오퍼레이션은 원자성이 있지만**, compare and set 같은 처리를 위해 **여러 명령어를 묶을 때는 Lua 스크립트** 사용
- Lua 스크립트도 그냥 쓰는 게 아니라, **서버에서 어떻게 관리되는지, 언제 올라가는지, 없으면 어떻게 다시 올라가는지**까지 라이브러리를 보며 깊게 확인

### 전사문 용어 정리

| 전사문 | 의미 |
|---|---|
| 라운드 로빈을 최소화 | 여러 키를 가져올 때 요청이 **여러 노드를 돌아가며 흩어지는 것**을 줄인다는 의미로 해석. (네트워크 왕복(round trip)을 줄인다는 의미일 수도 있음. 어느 쪽이든 해결책은 MGET + 해시 태그) |
| compare and set | CAS (Compare-And-Set). "값이 예상과 같을 때만 바꿔라" |
| 언제 올라가는 거고, 부족하다면 다시 | Lua 스크립트가 Redis에 언제 등록되고, 사라지면 어떻게 다시 등록되는지 |

## 1. 기본 개념

### 라운드 로빈
- 요청을 **여러 대상에 차례로 돌아가며** 보내는 방식 (카드를 한 장씩 돌리듯)

### 라운드 트립 (네트워크 왕복)
- Redis 명령 자체는 마이크로초 단위로 빠르지만, **요청 → 응답 네트워크 왕복**은 보통 수백 μs ~ 1ms
- `GET`을 100번 하면 대부분의 시간이 네트워크 대기
- `MGET`은 여러 키를 **한 번에 요청** → 왕복 1번 (물건 100개를 한 상자에 담아 한 번에 배송)

### Redis 클라이언트 라이브러리
- Java 애플리케이션이 Redis 서버와 대화할 때 쓰는 라이브러리 (연결 관리, 슬롯 계산, 명령 전송)
- Redis는 서버, 이것들은 내 코드 안에서 도는 라이브러리 (Caffeine, Protobuf처럼)

| | Lettuce (레터스) | Redisson (레디슨) | Jedis (제디스) |
|---|---|---|---|
| 성격 | 기본 클라이언트 | 고수준 기능 클라이언트 | 전통적 클라이언트 |
| 방식 | 비동기, 연결 공유 | 비동기 | 동기, 연결 풀 |
| Spring Boot 기본 | ✅ | ❌ (따로 추가) | 예전 기본 |
| 강점 | 가볍고 빠름, 클러스터 지원 | 분산 락(`RLock`), 분산 자료구조 | 단순함 |

- 발표자가 "라이브러리를 까봤다" = MGET 쪼개기, Lua 스크립트 재등록 같은 동작이 **이 라이브러리들 안에 구현**되어 있기 때문

### 이번에 나온 Redis 명령어

| 명령 | 하는 일 | 나온 곳 |
|---|---|---|
| `GET` / `SET` | 값 하나 읽기 / 쓰기 | 기본 |
| `MGET` | 여러 키 한 번에 읽기 | 가져올 데이터가 많다면? |
| `INCR` / `DECR` | 숫자 1 증가 / 감소 (원자적) | 좋아요, 쿠폰 재고 |
| `SADD` | Set에 추가 (이미 있으면 0 반환) | 좋아요 중복 방지 |
| `SISMEMBER` | Set에 있는지 확인 | Lua 검증 |
| `EVAL` | Lua 스크립트 실행 (전문 전송) | 원자적 처리 |
| `SCRIPT LOAD` / `EVALSHA` | 스크립트 등록 / SHA1 지문으로 실행 | 스크립트 관리 |
| `FUNCTION LOAD` / `FCALL` | Redis Functions 등록 / 이름으로 실행 | Redis 7+ |
| `WATCH` / `MULTI` / `EXEC` | 낙관적 트랜잭션 | CAS 비교 |

## 2. Redis Cluster 기초

### 왜 여러 대로 나누나
- **데이터가 많아서**: 한 대의 메모리에 다 안 들어감
- **요청이 많아서**: Redis는 명령을 하나씩 처리 → 한 대의 처리량에 한계
- → 데이터를 **여러 노드에 나눠 담는 것**이 Redis Cluster
- 핵심 질문: "이 키는 어느 노드에 저장하고, 나중에 어디서 찾지?" → 키만 보고 위치를 계산하는 규칙 필요

### 규칙: 키 → 슬롯 → 노드

```
키 ──(CRC16(키) % 16384)──▶ 슬롯 번호(0~16383) ──(슬롯 담당표)──▶ 노드
```

- **CRC16**: 글자를 숫자로 바꾸는 해시 함수. 같은 입력 → 항상 같은 결과, 조금만 달라도 전혀 다른 결과
- `user:1`, `user:2`처럼 이름이 비슷해도 **전혀 다른 슬롯으로 흩어짐** → 데이터가 골고루 퍼짐

```
슬롯 담당표 (예시)
노드 A: 슬롯 0 ~ 5460
노드 B: 슬롯 5461 ~ 10922
노드 C: 슬롯 10923 ~ 16383
```

- 비유: **노드 = 우체국**, **슬롯 = 우편번호**, **키 = 집 주소**

### 왜 슬롯을 거치나 (키 → 노드로 바로 안 가고)
- `% 노드수`로 바로 정하면 노드가 3→4대가 될 때 **약 75%의 키가 이사**
- 슬롯을 두면 **키 → 슬롯 계산은 영원히 고정**, 바뀌는 건 **슬롯 담당표**뿐
- 노드 D 추가 → A, B, C가 슬롯 일부를 D에게 넘김 → **넘긴 슬롯의 데이터만** 옮김 (약 25%)

### 슬롯 번호가 고정이면 노드 추가해도 상관없지 않나?
- 슬롯 번호는 고정이지만, **데이터는 실제로 어떤 노드의 메모리에** 있음
- 새 노드 D는 비어 있음 → 슬롯을 넘겨받아야 일을 함 → 그 슬롯의 데이터를 **실제로 D로 복사**해야 함
- 슬롯의 이점 = 노드 추가가 공짜가 되는 게 아니라, **옮길 데이터가 명확하고 최소화**되는 것

| | `% 노드수` | 슬롯 방식 |
|---|---|---|
| 노드 추가 시 바뀌는 것 | 키 → 노드 계산 자체 | 슬롯 → 노드 담당표 일부 |
| 옮길 데이터 | 약 75% (3→4대) | 약 25% |
| 어떤 키가 옮겨지나 | 키마다 다시 계산 | 넘긴 슬롯의 키 전부 (명확) |

- 옮기는 중 요청이 오면 `ASK` 응답으로 "지금 D로 옮기는 중이니 D에 물어보세요" → 무중단 증설 가능

### 슬롯 수는 항상 16384로 고정
- Redis 코드에 박혀 있어서 설정으로 못 바꿈
- **왜 16384?** (Redis 개발자 antirez 설명)
  - 노드끼리 주고받는 heartbeat에 "내가 맡은 슬롯 목록"을 비트로 담음 → 16384비트 = **2KB**. 65536개면 8KB라 부담
  - 권장 최대 노드 수 약 1000대 → 16384개면 노드당 16개 정도씩 나눠줄 수 있음
  - → **신호 크기와 분배 단위의 절충점**
- 다른 시스템 비교

| 시스템 | 나누는 단위 | 개수 변경 |
|---|---|---|
| Redis Cluster | 해시 슬롯 | 고정 (16384) |
| Cassandra | 토큰 링 + 가상 노드 | 설정 가능 |
| Kafka | 파티션 | 늘릴 수 있음. 단, 키 → 파티션 계산이 바뀌어 순서 보장 깨짐 (슬라이드 4 "파티션 증설") |

### 슬롯은 메모리가 아님
- 슬롯 = 키를 묶는 **번호표(논리적 구분)**. 공간을 미리 차지하지 않음
- 실제 메모리를 쓰는 건 **키와 값**. 키가 없는 슬롯은 사실상 0
- 관리용 정보(어떤 슬롯을 맡는지, 슬롯별 키 목록)는 약간 있지만 데이터에 비하면 아주 작음

### 노드가 하나일 때

| 구성 | 슬롯 | 여러 키 MGET·Lua |
|---|---|---|
| standalone (한 대) | 없음 | 자유롭게 가능 |
| primary + replica (Sentinel) | 없음 | 자유롭게 가능 |
| 클러스터 (노드 1대) | 16384개 전부 한 노드 | 같은 슬롯끼리만 |
| 클러스터 (노드 여러 대) | 노드들이 나눠 맡음 | 같은 슬롯끼리만 |

- ⚠️ **함정**: 로컬은 standalone이라 MGET·Lua가 잘 되다가, 운영 클러스터에서 CROSSSLOT 에러로 장애
  - → 테스트 환경도 운영과 같은 구성으로 (슬라이드 12 "H2 vs MySQL → Testcontainer")

### 한 노드가 슬롯을 다 맡을 수 있는데 왜 증설?
- 슬롯을 **맡을 수 있는 것** ≠ **감당할 수 있는 것**
- 슬롯은 번호표일 뿐, 그 슬롯의 데이터와 요청은 결국 **노드 한 대의 메모리와 CPU**로 처리
- 비유: 우체국 하나가 전국 우편번호를 다 맡을 수는 있지만, 우편물이 늘면 창고(메모리)와 직원(CPU)이 모자람
- 처음부터 클러스터 모드로 한 대를 쓰는 이유: 클러스터 규칙을 지키며 개발해두면 **나중에 코드 수정 없이** 노드만 추가 가능
- 슬롯 = "나눌 수 있게 미리 그어둔 선", 노드 증설 = "그 선을 따라 실제로 나누는 것"

### 노드를 늘리는 이유와 종류

| 상황 | 늘리는 것 | 이유 |
|---|---|---|
| 데이터가 너무 많음 | primary | 슬롯을 나눠 노드당 저장량 감소 |
| 쓰기 요청이 많음 | primary | 쓰기는 primary만 처리 |
| 읽기 요청이 많음 | replica도 가능 | replica에서 읽기 분산 |
| 장애 대비 | replica | primary 장애 시 승격 |

- ⚠️ **hotkey는 노드를 늘려도 해결 안 됨**: 키 하나 = 슬롯 하나 = 노드 하나

### 나누면 오히려 안 좋아지지 않나? → 트레이드오프
- 노드끼리 **소통은 함** (gossip): heartbeat, 슬롯 담당 공유, 장애 시 투표로 replica 승격, 슬롯 이동 시 데이터 전송
- 안 하는 것: **명령 하나를 여러 노드가 나눠서 함께 처리하는 것**

| 나누면 잃는 것 | 나누면 얻는 것 |
|---|---|
| 여러 키 MGET·Lua·트랜잭션이 같은 슬롯끼리만 | 한 대 메모리를 넘는 데이터 저장 |
| 흩어진 키는 여러 노드에 따로 요청 | 한 대 처리량을 넘는 요청 처리 |
| 해시 태그 설계, 슬롯 재배치 등 운영 부담 | 노드 하나가 죽어도 일부 슬롯만 영향 |

- 대부분의 Redis 사용은 **키 하나짜리 명령** (`GET user:123`, `INCR likes:456`) → 나눠도 잃는 게 없음
- 결론: 한 대로 충분하면 단순하게, 감당 안 되면 클러스터로 나누고 **잃는 부분은 설계로 보완**
- → 이번 슬라이드의 두 질문이 바로 **"나눴을 때 생기는 손해를 어떻게 줄이나"**

### 클라이언트는 어떻게 노드를 찾아가나
- 라이브러리가 시작할 때 **슬롯 담당표를 받아와서** 기억
- `GET user:1` → 라이브러리가 직접 슬롯 계산 → 담당 노드로 바로 전송
- 담당표가 오래돼서 잘못 보내면 `MOVED <슬롯> <노드주소>` 응답 → 라이브러리가 담당표 갱신
- → 슬라이드 "운영·장애 대응 — **topology refresh**"

## 3. 가져올 데이터가 많다면?

### CROSSSLOT: 왜 MGET이 그냥 안 되나

```
MGET user:1 user:2
  user:1 → 슬롯 15443 → 노드 C
  user:2 → 슬롯 6319  → 노드 B
→ (error) CROSSSLOT Keys in request don't hash to the same slot
```

- 명령 하나는 **노드 하나에서만** 실행됨
- 노드끼리 협력해서 처리하지 않는 이유: 느려지고 복잡해짐, 여러 노드에 걸친 원자성 보장이 매우 어려움 → Redis는 **"한 명령의 키는 모두 같은 슬롯"**이라는 단순한 규칙을 택함

#### MGET 자체가 안 되는 건 아님

| 상황 | MGET |
|---|---|
| standalone Redis | ✅ 아무 키나 |
| Cluster, 키들이 같은 슬롯 | ✅ |
| Cluster, 키들이 다른 슬롯 | ❌ CROSSSLOT |

#### "같은 노드"가 아니라 "같은 슬롯"
```
user:2 → 슬롯 6319 → 노드 B
user:7 → 슬롯 8000 → 노드 B
MGET user:2 user:7 → 그래도 CROSSSLOT 에러
```
- 지금은 같은 노드여도, 슬롯 8000이 나중에 다른 노드로 옮겨지면 같은 명령이 갑자기 실패하게 됨 → 처음부터 **슬롯 단위**로 규칙을 정함

### 라이브러리는 MGET을 어떻게 쪼개나
- 키 하나씩 GET이 아니라, **같은 슬롯끼리 묶어서 묶음마다 MGET**

```
mget(a, b, c, d, e, f)

① 슬롯 계산         ② 같은 슬롯끼리 묶기     ③ 묶음마다 MGET (동시에)
a → 슬롯 100 (A)     슬롯 100   : a, c        → A: MGET a c
b → 슬롯 7000 (B)    슬롯 7000  : b, e        → B: MGET b e
c → 슬롯 100 (A)     슬롯 12000 : d           → C: MGET d
d → 슬롯 12000 (C)   슬롯 300   : f           → A: MGET f
e → 슬롯 7000 (B)
f → 슬롯 300 (A)     ④ 원래 순서로 합쳐서 반환: [a, b, c, d, e, f]
```

- `a, c`와 `f`는 같은 노드 A인데도 따로 감 (슬롯이 달라서)
- Lettuce 등은 기본적으로 **슬롯 단위**로 묶는 것으로 알려짐 (정확한 동작은 라이브러리·버전마다 다르니 소스 확인 필요 → 발표자가 "까봤다"는 부분)
- **최악의 경우**: 해시 태그 없이 키 100개 → 슬롯 약 100개 → 키 1개짜리 MGET 약 100번 ≈ GET 100번
  - 비동기로 동시에 나가서 응답 시간은 "가장 느린 하나" 정도지만, Redis 명령 수와 네트워크 패킷은 그대로 100개
- 쪼개진 MGET은 **원자성도 없음**: 묶음마다 다른 순간에 실행 → 서로 다른 시점의 값이 섞일 수 있음

### 해시 태그: 같이 쓰는 키를 같은 슬롯에
- 키에 `{}`가 있으면 **그 안의 글자만** 해시해서 슬롯 결정

```
user:{123}:profile   → "123"만 해시 → 슬롯 X
user:{123}:grade     → "123"만 해시 → 슬롯 X (같은 슬롯!)
user:{123}:settings  → "123"만 해시 → 슬롯 X

MGET user:{123}:profile user:{123}:grade user:{123}:settings → 진짜 1번에 처리
```

- 비유: 같이 주문될 물건을 **처음부터 같은 창고에** 보관

#### `{1}`, `{2}`는 노드 번호가 아님
- `{1}` = "1번 노드로" ❌ / "1이라는 글자만 해시해라" ✅
- 보장하는 것은 딱 하나: **같은 태그 → 같은 슬롯**
- `{1}`과 `{2}`가 같은 노드일지 다른 노드일지는 모르고 신경 쓰지 않음 (해시 결과 + 담당표가 결정)
- 특정 노드를 지정하는 방식이었다면 증설 시 오히려 문제
- 태그에는 보통 **"같이 꺼내 쓸 묶음"의 대표값 = 엔티티 ID**

#### 너무 모으면 쏠림
```
❌ {all}:user:1 ~ {all}:user:1억 → 전부 슬롯 하나 = 노드 하나 (클러스터 무의미)
✅ {123}:profile, {123}:grade / {456}:profile, {456}:grade → 유저끼리는 흩어짐
```
- 원칙: **같이 쓰는 건 모으고, 전체는 흩어지게**

### MGET을 잘못 쓰면 부하가 커짐

| 잘못 쓰는 경우 | 문제 | 대응 |
|---|---|---|
| 흩어진 키 MGET | 코드는 한 줄인데 보이지 않게 요청 수백 개로 쪼개짐 | 같이 쓰는 키에 해시 태그 |
| 한 번에 키가 너무 많음 (예: 10만 개) | 실행 동안 Redis 전체가 멈춤, 응답도 큼 | 100~수백 개 단위로 나눠 보내기, slow command 모니터링 |
| 과도한 해시 태그 | 한 노드에 쏠림 (hotkey) | 태그를 작은 묶음 단위로 |

## 4. 원자적 처리가 필요하다면?

### 원자적(atomic)이란
- **중간에 아무도 끼어들 수 없이, 한 덩어리로 실행되는 것**
- Redis는 명령을 한 줄로 세워 하나씩 처리 → **명령어 하나는 원래 원자적**
  - `INCR likes:123` → 1000명이 동시에 눌러도 정확히 1000 증가
  - `SET lock:a 1 NX` → "없을 때만 저장"을 한 번에

### 문제: 명령어 여러 개를 묶을 때

```
선착순 쿠폰 (남은 수량 1장)
요청 A: GET → 1 (있네!)
요청 B: GET → 1 (있네!)   ← A가 DECR하기 전에 끼어듦
요청 A: DECR → 0
요청 B: DECR → -1          ← 없는 쿠폰 발급
```
- "확인하고 → 행동하기" 사이의 **틈**이 문제

### CAS (Compare-And-Set)
> "내가 아까 봤던 값이 아직 그대로일 때만 바꿔줘. 누가 그 사이에 바꿨으면 바꾸지 마."

```
철수: "지금 값이 10이면 9로" → 실제 10 = 예상 10 ✅ → 9
영희: "지금 값이 10이면 9로" → 실제 9 ≠ 예상 10 ❌ → 거절
영희: 다시 읽음 → "지금 값이 9면 8로" → ✅ → 8
```

1. 현재 값을 읽음 (예상값으로 기억)
2. 새 값 계산
3. **[한 번에]** 현재 값 == 예상값? → 같으면 저장, 다르면 실패 후 1번부터

- 다른 곳의 CAS
  - Java `AtomicInteger.compareAndSet(10, 9)`
  - DB 낙관적 락: `UPDATE ... WHERE id = 1 AND version = 1` (슬라이드 6 "lock — Optimistic")
  - Redis `WATCH` + `MULTI/EXEC`
- Redis에는 일반 값에 대한 CAS 명령이 기본으로 없음 → 여러 명령을 원자적으로 묶을 방법 필요

### Lua 스크립트: 여러 명령을 하나처럼
- Redis 서버 안에서 Lua 스크립트 실행, **스크립트 전체가 명령어 하나처럼** 취급 → 실행 중 다른 명령이 못 끼어듦
- 덤으로 **왕복도 1번**으로 줄어듦

```lua
-- 쿠폰 발급
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock and stock > 0 then
  redis.call('DECR', KEYS[1])
  return 1
end
return 0
```

```lua
-- 좋아요 (중복 방지 + 증가를 한 번에)
if redis.call('SADD', KEYS[1], ARGV[1]) == 1 then   -- 처음 누른 사람이면
  return redis.call('INCR', KEYS[2])                 -- 좋아요 수 +1
end
return -1                                            -- 이미 누름
```

```
EVAL "<스크립트>" 2 post:{123}:likers post:{123}:likes 철수
                  ↑키 개수 ↑KEYS[1]           ↑KEYS[2]          ↑ARGV[1]
```

#### CAS(WATCH) vs Lua vs 분산 락

| 방법 | 방식 | 특징 |
|---|---|---|
| `WATCH` + `MULTI/EXEC` | 키를 지켜보다 누가 바꿨으면 취소 → 재시도 | 낙관적 락. 경쟁이 심하면 재시도 반복 |
| Lua 스크립트 | 서버에서 한 번에 실행 | 재시도 없음, 조건 분기 가능, 왕복 1번 |
| 분산 락 | 락을 먼저 잡고 처리 | 무겁고 느림 (슬라이드 6 분산락) |

→ 전사문 "compare and set이 필요할 때 여러 명령어는 Lua 스크립트" = CAS가 필요한 상황을 Lua로 더 확실하게 처리

### 스크립트는 어느 노드에서 실행되나
- **KEYS로 넘긴 키**의 슬롯을 계산 → 그 슬롯의 **primary** 노드에서 실행 (`GET`이 노드를 찾아가는 것과 같은 원리)
- ⚠️ 키는 반드시 **KEYS로** 넘기기. 스크립트 안에 하드코딩하면 라이브러리·Redis가 볼 수 없어 엉뚱한 노드에서 실행됨

```lua
redis.call('INCR', 'post:{123}:likes')  -- ❌ 하드코딩
redis.call('INCR', KEYS[2])             -- ✅
```

| 상황 | 결과 |
|---|---|
| KEYS가 모두 같은 슬롯 | 그 노드에서 실행 ✅ |
| KEYS가 다른 슬롯 | **실행 전에 CROSSSLOT 에러** (스크립트 한 줄도 실행 안 됨) ❌ |
| KEYS 없음 | 아무 노드에나 |
| 담당표가 오래됨 | `MOVED` → 다시 보냄 |

- MGET은 쪼개서라도 동작하지만, **Lua는 쪼갤 수 없음** (쪼개면 원자성이 깨짐) → **해시 태그가 필수**

### 스크립트 관리: EVAL, SCRIPT LOAD, EVALSHA
> 비유: Lua 스크립트 = 레시피, Redis = 주방

| 명령 | 비유 | 장점 | 단점 |
|---|---|---|---|
| `EVAL` | 매번 레시피 전문을 읽어주며 주문 | 항상 동작 | 요청이 무거움 |
| `SCRIPT LOAD` | 레시피를 주방에 등록 → SHA1 번호 받음 | – | – |
| `EVALSHA` | 번호로 주문 | 요청이 가벼움 | 주방이 잊으면 실패 |

- SHA1 = 스크립트 내용으로 계산한 **지문**. 내용이 같으면 항상 같은 번호

#### 스크립트가 사라지는 경우
- Redis 스크립트 캐시는 **메모리에만** 있음
  - Redis **재시작**
  - 장애로 **replica가 primary로 승격**
  - `SCRIPT FLUSH`
- 이때 `EVALSHA` → **`NOSCRIPT` 에러** ("그런 메뉴 없는데요?")

#### 라이브러리가 자동으로 다시 올림 (Spring Data Redis, Redisson 등)
```
1. EVALSHA로 시도
2. NOSCRIPT 에러
3. EVAL로 전문 전송 → 실행되면서 Redis에 자동 재등록
4. 다음부터 다시 EVALSHA
```
→ 전사문 "언제 올라가는 거고, 부족하다면 어떻게 다시 되는 거지?"가 이 흐름

#### 스크립트 원본은 어디에?
- **원본 = 애플리케이션 코드 파일** (애플리케이션 쪽 디스크)
  1. 개발: `src/main/resources/scripts/like.lua` (Git 관리)
  2. 배포: 빌드된 jar 안에 포함
  3. 실행: 애플리케이션이 시작할 때 읽어서 자기 메모리에 문자열로 보관
- **사본 = Redis 메모리** (스크립트 캐시, 사라질 수 있음)

```java
RedisScript<Long> likeScript =
    RedisScript.of(new ClassPathResource("scripts/like.lua"), Long.class);
redisTemplate.execute(likeScript, keys, userId); // EVALSHA → (NOSCRIPT면) EVAL
```

#### 사본이 메모리에만 있어도 괜찮은 이유
- 사라졌을 때 비용 = **원본을 한 번 더 보내는 것**뿐. Redis 재시작은 드물어서 부담 거의 없음
- 메모리에 두는 목적은 **보관이 아니라 속도** (번호로 짧게 호출)
- 로컬 캐시와 같은 원리: **원본이 다른 곳에 확실히 있으면, 캐시는 사라지면 다시 채우면 된다**

| | 로컬 캐시 | 스크립트 캐시 |
|---|---|---|
| 원본 | 유저 서버, DB | 애플리케이션 코드 |
| 캐시 위치 | 게이트웨이 메모리 | Redis 메모리 |
| 사라지면 | 원본에서 다시 가져옴 | 원본을 다시 보냄 |

### Redis Functions (Redis 7.0+)
- Lua 코드를 **이름이 붙은 함수**로 Redis에 정식 등록 (비유: 레시피를 포스트잇이 아니라 **정식 메뉴판에 인쇄**)

```lua
#!lua name=couponlib
redis.register_function('issue_coupon', function(keys, args)
  local stock = tonumber(redis.call('GET', keys[1]))
  if stock and stock > 0 then
    redis.call('DECR', keys[1])
    return 1
  end
  return 0
end)
```
```
FUNCTION LOAD "<위 코드>"
FCALL issue_coupon 1 {coupon:A}:stock
```

| | EVAL / EVALSHA | Redis Functions |
|---|---|---|
| 부르는 방법 | 전문 또는 SHA1 | **함수 이름** |
| 저장 위치 | 메모리만 | 메모리 + **디스크** (RDB, AOF) |
| 재시작하면 | 사라짐 → NOSCRIPT | **남아 있음** |
| replica 복제 | 안 됨 | **복제됨** |
| 누가 올리나 | 애플리케이션이 그때그때 | 배포 시점에 **미리 등록** |
| 관리 | 목록 파악 어려움 | `FUNCTION LIST` |

- DB의 저장 프로시저와 비슷 → Redis가 원본을 책임지는 방식
- 고민할 점
  - **배포 순서**: 앱이 `FCALL`하기 전에 함수가 등록되어 있어야 함
  - **버전 관리**: `FUNCTION LOAD REPLACE`. 롤링 배포 중 옛/새 버전 앱이 공존할 때 둘 다 동작하게
  - **클러스터**: replica에는 복제되지만, **다른 샤드의 primary에는 자동 전파 안 됨** → 모든 primary에 각각 등록
- 정리: EVALSHA는 유연하지만 사라질 수 있음 / Functions는 튼튼하지만 배포·관리 필요

### 롤백이 없다 → 검증은 앞에, 쓰기는 뒤에
- ⚠️ Lua 스크립트 "원자적" = **다른 요청이 끼어들지 못한다** ≠ **실패하면 없던 일로 해준다**
- 중간에 에러가 나면 **에러 전에 실행된 쓰기는 그대로 남음** (DB 트랜잭션과 다름)

```lua
redis.call('SADD', KEYS[1], ARGV[1])   -- ① 성공
redis.call('INCR', KEYS[2])            -- ② 값이 "abc"라 에러
-- → 누른 사람 목록엔 있는데 좋아요 수는 안 오름 (절반만 실행된 상태)
```

- 해결: **확인은 먼저, 쓰기는 나중에 몰아서**

```lua
-- [1단계] 확인만 (아무것도 바꾸지 않음)
local count = redis.call('GET', KEYS[2])
if count and not tonumber(count) then
  return redis.error_reply('like count is not a number')
end
if redis.call('SISMEMBER', KEYS[1], ARGV[1]) == 1 then
  return -1
end
-- [2단계] 확인 끝난 뒤 쓰기
redis.call('SADD', KEYS[1], ARGV[1])
return redis.call('INCR', KEYS[2])
```

| 앞에서 확인할 것 | 예 |
|---|---|
| 값의 타입 | 숫자여야 하는 값이 숫자인지 (`tonumber`) |
| 키의 자료구조 | Set이어야 하는 키가 String이 아닌지 (`TYPE`) |
| 인자 | 비어 있거나 잘못되지 않았는지 |
| 비즈니스 조건 | 재고가 남았는지, 이미 처리됐는지 |

- 비유: 이사할 때 열쇠·엘리베이터·트럭부터 확인하고, 다 괜찮을 때 짐을 옮기기 시작

### 그 밖의 주의
- **짧게 쓰기**: 스크립트 실행 중엔 그 노드의 다른 모든 요청이 대기 → 슬라이드 "slow command"

### 과도한 해시 태그 쏠림은 Lua에서 더 두드러짐

| | MGET | Lua 스크립트 |
|---|---|---|
| 같은 슬롯이 아니면 | 쪼개져서 동작 (느려짐) | **실행 불가** |
| 태그로 모을 압박 | 선택 사항 | **필수** |
| 부하 분산 | replica 읽기 가능 | **primary만** |
| 노드를 막는 시간 | 짧음 | 상대적으로 김 |

- 예: "유저별 쿠폰 발급 기록" + "전체 쿠폰 재고"를 한 스크립트로 묶으면 모든 발급 기록이 `{coupon:A}` 하나로 → 노드 하나에 집중
- 설계 시: "이 스크립트가 다루는 키 묶음이 얼마나 많은 요청을 받을까?" → 묶음이 크면 스크립트를 쪼개거나 원자성이 꼭 필요한 부분만 남기기
- 단, 선착순 쿠폰처럼 **데이터 자체가 hotkey**면 Lua 여부와 무관 → 재고를 여러 키로 나누는 등 다른 설계 필요

### 내 경험과 연결: 좋아요 기능
- 당시 구조: 누가 눌렀는지는 **DB에서 판단** (`likes` 테이블 저장) + 좋아요 수는 **Redis `INCR`**
- 좋은 점: DB 유니크 제약으로 중복 방지 확실, 좋아요 수 읽기 부하는 Redis로 해결
- 아쉬운 점: 누를 때마다 DB 쓰기 발생, DB와 Redis 수가 어긋날 가능성
- 발전 방향
  - 누른 사람도 Redis Set(`SADD`)으로 판단 + **Lua로 `SADD` 성공 시에만 `INCR`** (원자적)
  - DB에는 모아서 반영 (write-behind, 캐시 슬라이드 "순간 요청량이 몰린다면?")
  - 주기적으로 DB `COUNT`로 Redis 값 보정
  - 키에 해시 태그 `post:{123}:likers`, `post:{123}:likes`
- 특별전형 소재: "읽기 부하는 해결했지만 쓰기·정합성 문제가 있었고, 이렇게 바꿀 수 있다/바꿨다" → **아키텍처 변화**

## 5. 두 질문이 만나는 지점
- 클러스터에서 Lua 스크립트를 쓰려면 **모든 KEYS가 같은 슬롯**이어야 함
- → **해시 태그로 슬롯을 설계하는 것**이 MGET 최적화와 Lua 원자 처리 **모두의 전제 조건**
- 두 질문 모두 결국 **"클러스터로 나눴을 때 생기는 손해를 어떻게 줄이나"**
  - 가져올 데이터가 많다면 → 흩어진 키로 늘어난 요청을 해시 태그 + MGET으로 줄이기
  - 원자적 처리가 필요하다면 → 슬롯이 나뉘어도 같은 슬롯에 모아 Lua로 묶기

## 6. 한 줄 요약

> **많이 가져올 때**: MGET으로 왕복을 줄이되, 클러스터에서는 라이브러리가 슬롯별로 쪼개 보내니 **해시 태그로 같이 쓰는 키를 같은 슬롯에** 모은다. 너무 모으면 쏠리고, 한 번에 너무 많이 가져오면 Redis가 멈춘다.
>
> **원자적으로 처리할 때**: 명령 하나는 원래 원자적이고, 여러 명령은 **Lua 스크립트로 묶는다.** 키는 KEYS로 넘기고 같은 슬롯이어야 한다. 스크립트는 SHA로 캐시되며 사라지면 라이브러리가 원본을 다시 보낸다(또는 Redis Functions로 영구 등록). **롤백이 없으니 검증은 앞에, 쓰기는 뒤에**, 그리고 짧게 쓴다.
