## 1. 캐시 버전 관리

DB와 Redis 간 데이터 불일치를 방지하고 최신 데이터가 유지되도록 관리하는
영역이다.

### 1.1 Dual Write

-   DB와 Redis 등 두 저장소에 각각 데이터를 기록하는 방식이다.
-   두 저장소는 일반적으로 하나의 트랜잭션으로 묶이지 않으므로 부분
    실패가 발생할 수 있다.
-   DB 변경은 성공했지만 Redis 갱신이 실패하면 오래된 캐시가 남을 수
    있다.
-   일반적인 Cache-Aside에서는 DB를 먼저 변경한 뒤 Redis 키를 삭제하고,
    다음 조회에서 캐시를 재생성하는 방식을 사용한다.

### 1.2 Cache Versioning

-   데이터에 버전을 부여해 캐시가 최신 데이터인지 판단하는 방식이다.
-   DB 데이터가 변경될 때 버전을 증가시키고, Redis에도 데이터와 버전을
    함께 저장한다.
-   오래된 데이터가 뒤늦게 캐시에 저장되는 문제(Stale Cache
    Resurrection)를 방지하는 데 활용한다.
-   버전 비교와 캐시 저장은 원자적으로 처리해야 하며, 버전 정보의 보존
    및 갱신 신뢰성도 고려해야 한다.

### 1.3 Read Version-up

-   읽기 과정에서 캐시의 버전을 확인하고 오래된 데이터라면 최신 데이터로
    갱신하는 방식이다.
-   캐시 버전과 최신 버전을 비교해 불일치를 감지한다.
-   매 요청마다 DB에서 버전을 조회하면 캐시의 성능 이점이 줄어들 수
    있으므로, 버전 정보를 어디서 어떻게 관리할지 설계해야 한다.

## 2. 순간 요청량 대응: Write-Behind

대량의 쓰기 요청이 DB에 집중되는 상황에서 Redis가 요청을 먼저 수용하고
DB에는 비동기로 반영하는 방식이다.

### 2.1 동작 흐름

1.  클라이언트의 쓰기 요청을 Redis에 기록한다.
2.  Redis에 기록된 데이터를 Consumer가 비동기로 읽는다.
3.  Consumer가 데이터를 DB에 적재한다.
4.  DB 반영이 완료되면 메시지 처리 완료를 기록한다.

### 2.2 특징

-   Redis가 DB 반영 전까지 최신 쓰기 데이터를 보유하는 1차 쓰기 기준점
    역할을 한다.
-   Consumer를 통해 DB 적재 속도를 조절할 수 있어 순간적인 쓰기 부하를
    완화할 수 있다.
-   일반적으로 DB는 최종 영속 저장소이며, Redis가 최종 SSOT가 되는
    것과는 구분해야 한다.

### 2.3 고려 사항

-   DB 반영 전에 Redis 장애가 발생하면 데이터가 유실될 수 있으므로
    영속성 및 복구 전략이 필요하다.
-   Consumer 재시도, 중복 처리 방지(Idempotency), Pending 메시지 복구를
    고려해야 한다.
-   Consumer 처리 지연, Stream 적체, 메모리 사용량을 모니터링해야 한다.
-   Redis Stream의 메시지 보존 및 트리밍 정책을 설계해야 한다.

## 3. 운영 및 장애 대응

Redis의 성능과 상태를 측정하고, 대량 데이터 처리 및 장애 상황에 안전하게
대응하는 영역이다.

### 3.1 Hit Rate

-   캐시 조회 중 적중한 비율이다.
-   `INFO stats`의 `keyspace_hits`, `keyspace_misses`를 활용해 계산한다.

``` text
Hit Rate = Hits / (Hits + Misses) * 100
```

-   `INFO commandstats`는 명령어별 호출 횟수와 실행 시간 등을 확인하는
    용도이며 Hit Rate를 직접 측정하는 지표는 아니다.
-   Redis 통계와 애플리케이션 수준의 실제 캐시 적중률은 다를 수 있으므로
    필요하면 애플리케이션에서도 Hit/Miss를 측정한다.

### 3.2 DEL과 UNLINK

-   `DEL`은 키를 삭제하고 메모리 해제를 동기적으로 처리할 수 있는
    명령어다.
-   `UNLINK`는 키를 논리적으로 먼저 제거하고 실제 메모리 해제를
    백그라운드에서 처리한다.
-   큰 데이터나 대량 키를 삭제할 때는 `UNLINK`가 Redis 처리 지연을
    줄이는 데 유리할 수 있다.

### 3.3 SCAN

-   Redis 키를 커서 기반으로 나누어 조회하는 명령어다.
-   `KEYS`처럼 전체 키를 한 번에 조회하는 방식보다 운영 환경에서
    안전하게 사용할 수 있다.
-   `COUNT`는 반환 개수를 보장하는 값이 아니라 조회량에 대한 힌트다.
-   조회 결과가 중복될 수 있으므로 중복 처리를 고려해야 한다.

``` text
SCAN 0 MATCH user:* COUNT 100
```

### 3.4 Indirection Key

-   실제 데이터 키를 직접 참조하지 않고 중간 참조 키를 통해 접근하는
    패턴이다.
-   예를 들어 `user:100:current`가 `v2`를 가리키고, 실제 데이터는
    `user:100:v2`에 저장하는 방식이다.
-   참조 키만 변경해 데이터 버전을 전환할 수 있어 여러 데이터를 준비한
    뒤 한 번에 공개하는 구조 등에 활용할 수 있다.
-   참조 키의 유실이나 잘못된 변경에 대비해야 한다.

### 3.5 Topology Refresh

-   Redis Cluster의 노드 구성과 SLOT 할당 정보를 클라이언트가 갱신하는
    작업이다.
-   노드의 역할(Master/Replica)이나 SLOT 담당 노드가 변경되면 기존
    클라이언트 정보가 오래된 상태가 될 수 있다.
-   `MOVED`는 해당 SLOT의 담당 노드가 변경되었음을 알리는 응답이다.
-   `ASK`는 SLOT 이동 중 지정된 노드로 일시적으로 요청하라는 응답이다.

### 3.6 Slow Command

-   Redis 내부에서 실행 시간이 오래 걸리는 명령어를 의미한다.
-   `SLOWLOG GET 10`으로 오래 걸린 명령어를 확인할 수 있다.
-   `SLOWLOG`는 Redis 내부 실행 시간만 측정하며 네트워크 지연이나
    애플리케이션 처리 시간은 포함하지 않는다.
-   API 응답 시간, 네트워크 지연 등과 함께 분석해야 한다.
