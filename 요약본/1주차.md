# 캐시 스터디 정리

캐시 설계의 핵심은 **캐시를 어디에 두고, 오래된 데이터를 어떻게 관리하며, 저장 비용을 어떻게 줄일 것인가**이다. 스터디 전사문을 세 가지 주제로 정리하고, 대화 중 혼동했던 개념을 보완했다.

> 구조의 변화는 전사문을 기준으로 정리했다. Cassandra의 구체적인 도입 방식은 원 발표 자료를 확인하지 못했으므로, 전사문에서 확인되는 설명과 해석을 구분했다.

## 1. 구조는 어떻게 진화했나?

```text
User Server + Remote Cache
→ Gateway + User Server
→ Gateway + Passport
→ Gateway + Local Cache + Sticky Session
→ Gateway + Cassandra
```

각 단계는 해결하려는 문제가 다르다. 다음 단계로 넘어갔다고 이전 기술을 모두 제거했다는 뜻은 아니다.

| 단계 | 해결하려는 문제와 접근 | 남는 과제 |
| --- | --- | --- |
| User Server + Remote Cache | 사용자 정보를 캐시에 저장해 DB 조회를 줄인다. | 캐시를 사용해도 User Server 호출과 네트워크 통신은 발생한다. |
| Gateway + User Server | 사용자 확인과 인증 등 공통 처리를 Gateway에 모은다. | Gateway에서 User Server를 계속 호출한다면 조회 병목은 남는다. |
| Gateway + Passport | 사용자 정보를 요청에 함께 전달해 내부 서비스들의 중복 조회를 줄인다. | Passport를 만들기 위한 조회 비용과 정보의 최신성을 관리해야 한다. |
| Gateway + Local Cache + Sticky Session | Gateway 메모리에서 정보를 재사용하고, 같은 사용자의 요청을 같은 Gateway로 보내 캐시 활용도를 높인다. | 서버별 데이터 차이, 재시작 시 캐시 소멸, 트래픽 쏠림을 관리해야 한다. |
| Gateway + Cassandra | 전사문 후반에서는 사용자 서비스 장애에도 필요한 정보를 사용할 수 있도록 별도 저장소를 두는 방향으로 설명한다. | 저장소에 정보를 반영하는 방법과 허용할 데이터 지연을 정해야 한다. |

### 1.1. Gateway: 공통 처리의 집중

Gateway는 인증, 사용자 확인, 라우팅 등 공통 처리를 한곳으로 모으는 역할을 한다.

**Gateway를 추가하는 것만으로 사용자 조회 횟수가 줄어드는 것은 아니다.** Gateway가 요청마다 User Server를 호출한다면 조회 비용은 여전히 발생한다. 반복 조회를 줄이는 역할은 Passport와 캐시가 담당한다.

### 1.2. Passport: 요청 내부의 중복 조회 감소

Passport는 필요한 사용자 정보를 묶어 내부 서비스로 전달하는 방식이다.

```text
Gateway에서 사용자 정보 확보
  → Passport를 요청에 첨부
  → 서비스 A → 서비스 B → 서비스 C

각 서비스는 전달받은 Passport에서 필요한 정보를 사용한다.
```

각 서비스가 동일한 사용자 정보를 얻기 위해 User Server를 반복 호출하는 대신, 요청에 담긴 정보를 재사용한다.

토스 공식 설명에서도 각 서비스의 반복적인 유저 API 호출을 줄이기 위해 Netflix의 Passport 구조를 참고했다고 설명한다. 따라서 전사문의 “Netflix가 만든 오픈소스를 사용했다”는 표현보다는 **“Netflix의 구조를 참고해 토스에 맞게 구현했다”**가 정확하다. [토스의 Gateway·Passport 설명](https://toss.tech/article/slash23-server)

Passport와 캐시는 재사용 범위가 다르다.

| 방식 | 재사용 범위 |
| --- | --- |
| Passport 전파 | 하나의 요청이 여러 서비스를 거치는 동안 사용자 정보를 재사용 |
| Local Cache | 같은 서버에 들어오는 여러 요청 사이에서 정보를 재사용 |
| Remote Cache | 여러 서버가 공통 저장소의 정보를 재사용 |

### 1.3. Local Cache + Sticky Session: 요청 사이의 재사용

Local Cache는 애플리케이션 프로세스의 메모리에 정보를 저장해 재사용한다. 원격 캐시에 접근하는 네트워크 비용을 줄일 수 있지만 서버마다 별도의 복사본이 생긴다.

Sticky Session은 같은 사용자의 요청을 같은 서버로 보내는 라우팅 방식이다.

```text
사용자 A → Gateway 1 → Gateway 1의 Local Cache
사용자 B → Gateway 2 → Gateway 2의 Local Cache
```

같은 서버의 로컬 캐시를 다시 사용할 가능성은 높여주지만, **원본 정보가 바뀌었을 때 캐시를 최신화해 주지는 않는다.**

### 1.4. Cassandra: 장애 시에도 필요한 정보 활용

Cassandra 도입 목적은 전사문에서도 의견이 갈렸다. 후반부의 “사용자 서비스가 내려가도 다른 서비스가 동작하도록 보완한다”는 설명을 기준으로 보면, **마지막으로 확보한 사용자 정보를 별도 저장소에서 활용해 장애 영향을 줄이는 구조**로 해석할 수 있다.

다만 원 발표 자료가 없어 실제 저장 데이터와 조회 순서, 기존 캐시의 유지 여부까지 확정할 수는 없다.

Cassandra는 분산 NoSQL 데이터베이스이며 대용량 처리와 높은 가용성을 목표로 설계됐다. “NoSQL이므로 캐시보다 빠르다”거나 “여러 DB를 자동으로 연결해 준다”는 의미는 아니다. [Cassandra 공식 아키텍처 설명](https://cassandra.apache.org/doc/latest/cassandra/architecture/overview.html)

## 2. Remote–Local 정합성은 어떻게 관리하나?

### 2.1. Stale 데이터의 의미

Stale 데이터는 **원본과 달라진 오래된 데이터**이다. 단순히 자주 사용하지 않는 데이터와는 다르다.

예를 들어 공유 저장소의 사용자 이름이 바뀌어도 Gateway의 로컬 캐시에는 이전 이름이 남아 있을 수 있다.

```text
변경 전
공유 저장소: 김토스
Gateway A:  김토스
Gateway B:  김토스

변경 후
공유 저장소: 이토스
Gateway A:  김토스 ← stale
Gateway B:  김토스 ← stale
```

정합성 관리의 핵심은 **오래된 데이터가 어느 서버에, 얼마나 오래 남을 수 있는지 관리하는 것**이다.

### 2.2. 변경 이벤트를 통한 캐시 무효화

전사문에서 다룬 기본 방식은 변경 사실을 각 서버에 알리고 해당 로컬 캐시를 삭제하는 것이다.

1. 원본 데이터를 변경한다.
2. 공유 캐시를 갱신하거나 무효화한다.
3. 해당 사용자의 정보가 바뀌었다는 이벤트를 발행한다.
4. 각 Gateway가 이벤트를 받아 해당 로컬 캐시를 삭제한다.
5. 다음 요청에서 최신 정보를 조회하고 로컬 캐시를 다시 채운다.

캐시를 삭제한 직후의 첫 요청은 **캐시 미스**이다. 새 정보를 채운 뒤 들어오는 요청부터 캐시 히트가 된다.

이 흐름만으로 동시성 문제까지 모두 해결되는 것은 아니다. 데이터 변경과 이벤트 발행 사이의 실패나, 변경 전에 시작한 조회 결과가 뒤늦게 캐시에 들어오는 상황도 별도로 고려해야 한다.

### 2.3. Pub/Sub과 Stream의 차이

| 구분 | Pub/Sub | Stream |
| --- | --- | --- |
| 기본 방식 | 현재 구독 중인 서버에 메시지를 전달 | 이벤트를 기록하고 소비자가 읽음 |
| 연결이 끊겼을 때 | 그동안의 메시지를 놓칠 수 있음 | 기록이 남아 있으면 이후에 읽을 수 있음 |
| 재처리 | Redis Pub/Sub 자체에서는 지원하지 않음 | 소비 위치를 이용해 재처리 가능 |
| 관리할 요소 | 구독 연결과 메시지 처리 | 보관 기간, 소비 위치, 재시도, 중복 처리 |

Redis Pub/Sub은 메시지를 놓치면 다시 전달하지 않는 방식이다. Stream은 이벤트 이력과 소비 상태를 활용할 수 있지만, 복구 가능 범위는 보관·영속성 설정과 소비 방식에 따라 달라진다. [Redis Pub/Sub 문서](https://redis.io/docs/latest/develop/pubsub/), [Redis Streams 문서](https://redis.io/docs/latest/develop/data-types/streams/)

로컬 캐시 무효화에서는 **모든 Gateway가 변경 사실을 알아야 한다.** Redis Streams에서 모든 Gateway를 하나의 Consumer Group에 넣으면 메시지가 분담 처리된다. 따라서 각 Gateway에 변경이 전파되도록 독립적인 소비 위치나 별도 그룹 등을 설계해야 한다.

### 2.4. TTL과 이벤트를 함께 사용하기

이벤트로 빠르게 무효화하고, 이벤트를 놓친 캐시도 일정 시간이 지나면 만료되도록 TTL을 함께 사용할 수 있다.

토스 공식 글의 작성자 답변에서도 짧은 TTL과 Redis Pub/Sub을 함께 사용한다고 설명한다. [토스의 캐시 무효화 설명](https://toss.tech/article/slash23-server)

다만 TTL이 있다고 최신성이 자동으로 보장되지는 않는다. 만료 후 조회하는 저장소도 오래된 상태라면 다시 오래된 정보를 채울 수 있다.

설계할 때는 다음을 정해야 한다.

- 변경 후 몇 초 또는 몇 분까지 이전 값을 허용할 것인가?
- 이벤트를 놓친 서버는 어떻게 복구할 것인가?
- 장애 중 마지막으로 저장한 정보를 사용해도 되는가?

## 3. 캐시가 차지하는 메모리가 커지면 어떻게 하나?

전사문의 “메모리가 크다면”은 **캐시가 차지하는 메모리가 커졌다면 어떻게 줄일 것인가**로 이해할 수 있다. 다만 Bitmap, Hot Key, Binary Format은 각각 다른 문제를 다룬다.

| 항목 | 다루는 문제 |
| --- | --- |
| Bitmap | 참·거짓 정보를 더 적은 공간으로 표현 |
| Hot Key | 특정 키에 요청이 집중되는 현상 |
| Binary Format | 객체를 저장·전송하는 바이트 표현을 간결하게 구성 |

### 3.1. Bitmap: 참·거짓 정보를 비트로 표현

Bitmap은 출석 여부나 특정 기능 사용 여부처럼 사용자별로 0 또는 1만 필요한 정보에 적합하다.

```text
키: attendance:2026-11-17

사용자 위치: 0 1 2 3 4 5
출석 여부:  1 0 1 1 0 1
```

Redis에서는 다음과 같이 사용할 수 있다.

```redis
SETBIT attendance:2026-11-17 3 1
GETBIT attendance:2026-11-17 3
BITCOUNT attendance:2026-11-17
```

- `SETBIT`: 3번 위치에 출석 여부를 표시한다.
- `GETBIT`: 3번 위치의 값을 조회한다.
- `BITCOUNT`: 값이 1인 비트의 수를 센다.

Redis Bitmap은 String을 비트 단위로 다루는 기능이다. [Redis Bitmap 문서](https://redis.io/docs/latest/data-types/bitmaps/)

1억 개의 상태를 1비트씩 저장하면 **비트 데이터 자체는 약 12.5MB**이다. 키와 내부 관리 비용은 별도다.

주의할 점은 실제 사용자 수보다 **가장 큰 비트 위치**가 공간에 영향을 준다는 것이다. 사용자 ID가 드문드문 크거나 UUID라면 그대로 비트 위치로 쓰기 어렵기 때문에, 연속된 번호로 매핑하거나 다른 자료구조를 검토해야 한다.

### 3.2. Hot Key: 특정 키에 집중되는 요청

Hot Key는 자료구조가 아니라 **요청이 유난히 많이 몰리는 키**이다.

- 데이터가 작아도 요청이 많으면 Hot Key일 수 있다.
- 큰 데이터라도 조회가 적으면 Hot Key가 아닐 수 있다.

읽기 요청이 집중되는 키는 로컬 캐시로 일부 요청을 흡수할 수 있다. 대신 로컬 복사본이 늘어나므로 무효화와 TTL 관리가 필요하다. [Redis의 Hot Key 대응 설명](https://redis.io/docs/latest/operate/rs/monitoring/observability/)

따라서 Hot Key 대응의 직접적인 목적은 **요청 집중과 부하를 줄이는 것**이다. 메모리 사용량 감소와는 구분해서 봐야 한다.

### 3.3. Binary Format: 저장 표현을 간결하게 구성

Binary Format은 객체를 JSON 대신 MessagePack이나 Protocol Buffers 같은 바이너리 형식으로 직렬화하는 방법이다.

| 형식 | 특징 | 고려할 비용 |
| --- | --- | --- |
| JSON | 사람이 읽기 쉽고 도구 지원이 넓음 | 필드명과 텍스트 표현의 크기 |
| MessagePack | JSON과 유사한 데이터를 바이너리로 표현 | 사람이 바로 읽기 어려움 |
| Protocol Buffers | `.proto` 스키마를 정의하고 필드 번호와 타입에 따라 표현 | 스키마 변경과 호환성 관리 |

MessagePack과 Protocol Buffers는 모두 직렬화 형식이다. Protocol Buffers는 필드명 대신 필드 번호 등을 사용하며 스키마를 공유해 데이터를 해석한다. 실제 크기와 처리 성능은 데이터에 따라 비교해야 한다. [MessagePack 명세](https://github.com/msgpack/msgpack/blob/master/spec.md), [Protocol Buffers 인코딩 설명](https://protobuf.dev/programming-guides/encoding/)

### 3.4. 직렬화·압축·암호화 구분

| 개념 | 목적 | 예시 |
| --- | --- | --- |
| 직렬화 | 객체를 저장·전송 가능한 표현으로 변환 | JSON, MessagePack, Protobuf |
| 압축 | 데이터의 크기를 줄임 | gzip, Zstandard |
| 암호화 | 키가 없는 사람이 내용을 읽기 어렵게 보호 | AES |

**JSON도 직렬화 형식이고, 바이너리 직렬화는 암호화가 아니다.** 직렬화한 결과를 추가로 압축하는 것도 가능하다.

```text
객체
  → 직렬화
  → 필요하면 압축
  → 저장 또는 전송

읽을 때는 반대 순서로 처리한다.
```

캐시에 적용할 때는 저장 크기뿐 아니라 직렬화·역직렬화 CPU 비용과 운영 편의성도 함께 봐야 한다. 로컬 캐시에 역직렬화한 객체를 보관한다면, 원격 저장 바이트를 줄인 만큼 로컬 객체 메모리까지 줄어드는 것은 아니다.
