진행자 한 줄
- Lua 스크립트가 처음엔 잘 와닿지 않았는데, 쿠폰이 한 장 남았을 때 두 요청이 동시에 남은 수량을 확인하면 재고가 -1이 될 수 있다는 예시를 듣고 왜 확인과 차감을 한 번에 처리해야 하는지 이해됐다.

대화에서 새로 알게 된 것
- Redis Cluster는 키를 해시 슬롯에 배정하고, 각 노드는 자신이 맡은 슬롯의 키를 처리한다. user:{1001}:email과 user:{1001}:age처럼 같은 해시 태그를 쓰면 관련 키를 같은 슬롯에 배치해 MGET으로 함께 조회할 수 있다.
- 조회할 키를 이미 알고 있으면 GET이나 MGET을 쓸 수 있다. 키를 탐색할 때는 SCAN을, 자료구조 내부를 점진적으로 순회할 때는 HSCAN(해시), SSCAN(집합), ZSCAN(정렬 집합)을 쓴다.
- Lettuce의 Advanced Cluster API처럼 여러 슬롯에 걸친 조회를 내부적으로 나눠 보내고 결과를 합쳐 주는 클라이언트도 있다. 애플리케이션에서는 한 번 호출해도 Redis Cluster에는 여러 명령이 전달될 수 있다.
- 원본 데이터가 따로 있다면 관련 캐시 키를 삭제한 뒤, 다음 조회에서 캐시 미스가 발생할 때 원본을 읽어 캐시를 다시 채울 수 있다. Lua 실행 오류는 Redis의 오류 응답으로 확인할 수 있다.

바로잡힌 오해
- DECR이 원자적이면 재고 확인과 차감도 안전할까? 쿠폰이 한 장 남았을 때 두 요청이 각각 GET으로 1을 읽고 차감하면 최종 재고는 -1이 될 수 있다. Redis에서 재고 확인과 조건부 차감을 하나의 Lua 스크립트로 실행하면 두 단계 사이에 다른 요청이 끼어들 수 없다.
- Redis는 원자성을 포기했을까? Redis는 개별 명령과 Lua 스크립트를 원자적으로 실행한다. Cluster에서는 여러 키를 사용하는 명령이나 스크립트에 같은 슬롯 제약이 적용된다. 스크립트 실행 중 오류가 나면 앞서 적용된 변경은 자동으로 롤백되지 않는다.
- 파이프라이닝으로 명령을 묶으면 원자성도 생길까? 파이프라이닝은 각 응답을 기다리지 않고 여러 명령을 보내 네트워크 왕복 비용을 줄인다. 각 명령의 실행은 독립적이다.

키워드끼리 연결된 지점
- 파티셔닝 → 해시 슬롯 → 리샤딩. 범위 파티셔닝은 날짜나 ID 범위로 데이터를 나누고, 해시 파티셔닝은 해시 결과를 기준으로 분산한다. Redis Cluster에서는 해시 슬롯을 여러 노드에 나눠 맡기고, 노드가 추가되거나 부하가 치우치면 슬롯을 노드 사이에서 옮겨 재분배할 수 있다.
- 원격 캐시 조회 → MGET·파이프라이닝. 원격 Redis에서 키를 여러 개 읽을 때 MGET은 여러 값을 한 명령으로 조회하고, 파이프라이닝은 여러 명령의 응답을 매번 기다리는 비용을 줄인다. 함께 읽는 키에 해시 태그를 쓰면 Cluster에서도 같은 슬롯에 배치할 수 있다.
- Lua 원자성 → 로컬 캐시 무효화. Lua로 Redis 안의 재고 확인과 차감을 한 번에 처리해도 애플리케이션의 로컬 캐시에는 이전 값이 남을 수 있다. 차감의 원자성과 갱신 결과가 각 캐시에 반영되는 시점은 별도로 다뤄야 한다.
